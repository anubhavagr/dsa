## 🔥 Pattern of the Day: 0/1 Knapsack on a 1-D Array
Each item is usable at most once, so while item i is being processed the array must
still describe the world of items 0..i-1. Squashing the classic dp[i][s] table into
one dimension preserves that only if capacity is walked in REVERSE: the value read
at dp[s - n] is then guaranteed to be pre-item, i.e. the previous row. Walk forward
and you re-read values this very item just wrote — silently upgrading the problem
to unbounded knapsack (tomorrow's topic, today's bug).
Invariant to recite at the whiteboard: **after item i is processed, dp[s] answers
"does some subset of items[0..i] sum to s?"** — and mid-item, dp[s - n] is still
the answer for items[0..i-1] only.

```python
def can_partition(nums: list[int]) -> bool:
    total = sum(nums)
    if total % 2:
        return False
    target = total // 2
    dp = [False] * (target + 1)   # dp[s]: can a subset of items seen SO FAR sum to s?
    dp[0] = True                  # the empty subset
    for n in nums:                            # each item used at most ONCE
        for s in range(target, n - 1, -1):    # REVERSE: dp[s-n] is still the pre-item row
            dp[s] = dp[s] or dp[s - n]
    return dp[target]
```

**Worked example** — `nums = [1, 5, 11, 5]`, `total = 22`, `target = 11`. Each row lists the sums whose dp slot is True after that item is processed:

| item processed | reachable sums (dp[s] = True) |
|---|---|
| 1  | 0, 1 |
| 5  | 0, 1, 5, 6 |
| 11 | 0, 1, 5, 6, 11 |
| 5  | 0, 1, 5, 6, 10, 11 |

dp[11] flips True on the second 5 (6 + 5), so the array splits as [11] vs [1, 5, 5].
Why reverse is load-bearing: with the single item 3 and target 6, a forward loop
would read dp[3] — written by this same item — and claim 3 + 3 from one copy of 3.

Self-check before the problems:
- Why does the inner loop stop at `n - 1` instead of running to 0?
- What breaks, concretely, if the inner loop runs 0 → target instead?
- If an item's value exceeds the target entirely, what does the range expression make its inner loop do — and is that correct?
