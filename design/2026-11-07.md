## ✏️ Phase 2 — One-page design (25 min)
- [ ] API / interface sketch
  - initiateUpload() → resumable session; completeUpload() → transcode ticket; playback(video_id, rendition) → manifest/segment URLs
- [ ] Data model + storage choice justified out loud
  - Blob store for segments, sharded SQL + cache for metadata — two different stores, two different reasons
- [ ] Box-and-arrow diagram — every box gets a one-line reason
  - Keep it ≤8 boxes; past that, group boxes and name the groups
- [ ] Upload path: resumable chunks → blob store
- [ ] Transcode pipeline drawn as a DAG: qualities (240p→4K), codecs (H.264/VP9/AV1), audio tracks, thumbnails, HLS/DASH segmentation
  - Draw it AS a DAG with named stages — the fan-out of renditions × codecs is the point of the picture
- [ ] CDN strategy: segments at the edge, hit-rate target, origin shield in front of origin
- [ ] View-count path: client events → stream → aggregated counters — not transactional increments
- [ ] Scaling story: partition key chosen + hot spots named
  - Partition by video_id for blobs/segments; the hot spot is a brand-new viral video with zero edge copies
- [ ] Failure story: what's lost on crash, replication, honest CAP position
  - Upload durable before "done" shows; a lost transcode job is re-runnable — say which failures are which class

## 🔥 Phase 3 — Escalations (20 min — answer ALOUD before opening Phase 4)
- [ ] E1: a new video goes viral — cold start on CDN: how do edges pull the origin without melting it?

## 📖 Phase 4 — Reference checkpoints (open only AFTER your attempt)
What a strong L5 answer includes:
- Resumable chunked upload to a GCS/S3-style blob store — a failed upload resumes, not restarts
  - Say it: "Upload is chunked and resumable — a failed 4GB upload resumes at the last chunk, not byte zero."
- Async transcode pipeline as a DAG: 240p→4K, H.264/VP9/AV1, audio tracks, thumbnails, HLS/DASH segmentation
- CDN serves segments at ~95%+ hit rate; origin shield sits between edges and origin — collapse cold-start fan-in
  - Say it: "Edges miss, the shield collapses the miss fan-in to one origin read per segment."
- Adaptive bitrate = the player picks the NEXT segment by measured bandwidth (buffer-based), not the server picking for it
  - Say it: "The player chooses the next segment from measured bandwidth — the server never picks a quality for the client."
- Popularity is long-tail: transcode eagerly only for predicted-hot or first-N-watches content; the rest lazy/on-demand
  - Say it: "Popularity is a long tail — eager transcode for the predicted-hot head, lazy for everything else."
- Viral cold start → origin shield + prefetch triggered by rising-edge detection
- View counting = client events → stream → aggregated counters with session dedup; NEVER transactional increments per view
  - Say it: "A view is an event on a stream feeding aggregated counters — nobody increments a row per watch."
- Metadata in sharded SQL + cache — small rows, high QPS, a different animal from the blob store
- Storage is PB/year class — erasure coding, cold tiers for old long-tail content
- Recommendations and search are SEPARATE systems — say the boundary out loud
  - Say it: "Recommendations and search are separate systems — this design hands them a video ID and stops."
