## ✏️ Phase 2 — One-page design (25 min)
- [ ] API / interface sketch
  - produce(topic, key, payload) → {offset}; consume(group, partition_assignments) → batch; commitOffsets(group, offsets)
- [ ] Data model + storage choice justified out loud
  - Partitioned append-only log; each partition = segment files + sparse offset index on disk — sequential IO is the whole design, say it
  - Say why sequential appends beat random writes BEFORE naming Kafka — the physics is the answer, the product is a footnote
- [ ] Box-and-arrow diagram — every box gets a one-line reason
  - Keep it ≤8 boxes; past that, group boxes and name the groups
- [ ] Consumer offsets: where stored, when committed, what a commit means (and doesn't)
- [ ] Delivery semantics ladder built out loud: at-least-once → the exactly-once illusion, rung by rung
- [ ] Scaling story: partition key chosen + hot spots named
  - Key-hash partitioning: ordering is per-partition, NOT per-topic — say the consequence; hot spot = one popular key lands on one partition
- [ ] Failure story: what's lost on crash, replication, honest CAP position
  - Leader partition dies → follower promotes; acks before replication = loss window — take a position

## 🔥 Phase 3 — Escalations (20 min — answer ALOUD before opening Phase 4)
- [ ] E1: exactly-once: why is it an illusion at the consumer, and how do idempotency keys + transactional offsets get close?
  - Probe: "process message" + "commit offset" is two steps — what dies between them?

## 📖 Phase 4 — Reference checkpoints (open only AFTER your attempt)
What a strong L5 answer includes:
- Topic → partitions by key hash; ordering per PARTITION, not per topic — the sentence is said explicitly
  - Say it: "Ordering is per PARTITION, not per topic — key-hash decides which order exists."
- Append-only log = segment files + sparse index → sequential IO, the reason disks keep up at 1M msg/s
  - Say it: "Segments plus a sparse index — the disk only ever appends and seeks forward."
- Consumers PULL with flow-control credits — backpressure is natural, not bolted on
  - Say it: "Consumers pull with credits — backpressure is the protocol, not a patch."
- Consumer groups: each partition owned by ONE consumer in a group; offsets committed by the group
- Rebalancing on failure = partition ownership handoff with pause-and-resume semantics — and you say the stop-the-world cost
- At-least-once is the base truth; everything stronger is built on top of it
- Exactly-once illusion = idempotent producers (producer id + sequence numbers) + transactional offset commits (consume-offset and produce-commit in ONE transaction)
  - Say it: "At-least-once is physics; exactly-once is idempotent producers plus transactional offsets — the illusion done carefully."
- Replay = offsets retained past consumption within the retention window — the log is the source of truth, not per-consumer queues
  - Say it: "The log IS the source of truth — replay is a new reader at an old offset, within retention."
- 1M subscribers = many consumer GROUPS; broker fans out to group leaders/aggregators, not to individuals
- Hot partition: cannot split a key's order — mitigate by key salting only if order allows; otherwise scale that partition's consumer vertically or add read replicas
  - Say it: "You can't split one key's order — salt the key if order allows, else throw hardware at that partition."
