## ✏️ Phase 2 — One-page design (25 min)
- [ ] API / interface sketch
  - suggest(prefix, user_context?, locale) → ranked top-10 + metadata; latency budget stated in the contract
- [ ] Data model + storage choice justified out loud
  - Trie with top-K suggestions materialized AT each node — why query-time ranking loses
- [ ] Box-and-arrow diagram — every box gets a one-line reason
  - Keep it ≤8 boxes; past that, group boxes and name the groups
- [ ] Build pipeline: logs → aggregation → top-K → publish
  - Offline MapReduce or streaming aggregation; snapshot or delta publish — and how often
- [ ] Tiered cache: browser → CDN edge → serving tier
  - What each tier caches (full-prefix results? prefill lists?) and its TTL
- [ ] Shard strategy for the trie — by prefix, with hot-letter handling
  - Say why per-node top-K beats query-time ranking BEFORE drawing — it IS the data model
- [ ] Scaling story: partition key chosen + hot spots named
  - Hot spots: single-letter prefixes (w, t, a...) dominate traffic — say it before drawing
- [ ] Failure story: what's lost on crash, replication, honest CAP position
  - Stale suggestions are acceptable; a dropped keystroke is not — where does that put you on CAP?

## 📖 Phase 4 — Reference checkpoints (open only AFTER your attempt)
What a strong L5 answer includes:
- Top-K suggestions materialized at each trie node, not computed at query time — the single most important decision
  - Say it: "Every node carries its top-10 materialized — a query is a walk, not a search."
- Build = offline MapReduce / streaming aggregation → publish snapshot or delta to serving tier
  - Say it: "The trie is BUILT offline from logs and published as snapshots or deltas — the serving tier never aggregates."
- Freshness tier: streaming trending overlay merged into results at serve time
  - Say it: "Trending rides a separate streaming overlay merged at serve time — the hours-long rebuild never gates minutes-old trends."
- Tiered caching with browser-side prefill — most keystrokes never leave the device
- Sharding by prefix with hot-letter splitting (a, s, t get sub-shards by second character)
  - Say it: "a, s, t get sub-shards on the second character — the hot letters pay for their own fan-out."
- Fallback to full search on trie miss — autocomplete is a suggestion system, not a source of truth
- Personalization = client-side recent searches prepended, NOT per-user state on servers
  - Say it: "Personalization is the client prepending its own recent searches — no per-user state server-side."
- Memory math shown: 10M queries × avg chars × per-node top-K struct → total RAM with headroom
  - Say it: "Ten million queries at ~15 characters with a small top-K struct per node is single-digit GB per replica — RAM-sized, not disk-sized."
- p99 budget split across tiers — browser (0) + edge (~10ms) + serving (~50ms) + merge
