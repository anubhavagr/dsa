## ✏️ Phase 2 — One-page design (25 min)
- [ ] API / interface sketch
  - send(msg, idempotency_key) / list(label, page_token) / search(query) / push subscribe
- [ ] Data model + storage choice justified out loud
  - Immutable message blob + normalized metadata rows (labels, flags, headers) — write-once, mutate metadata only
- [ ] Box-and-arrow diagram — every box gets a one-line reason
  - Keep it ≤8 boxes; past that, group boxes and name the groups
- [ ] Per-user partitioning: user → shard, everything for one mailbox co-located
  - One shard holds the mailbox AND its index — search and read stay local; say what that costs at rebalance time
- [ ] Search index architecture: inverted index local to each user's shard — search fans out within a mailbox, not across the planet
- [ ] Push: long-poll/websocket fan-out per user
- [ ] Sending path: durable queue + retries + idempotency keys at each delivery target
- [ ] Scaling story: partition key chosen + hot spots named
  - Partition by user_id; hot spots = one user with 10k labels, one viral thread — both rare, both survivable
- [ ] Failure story: what's lost on crash, replication, honest CAP position
  - Durability first: WAL + 3× replication before ack to sender; search freshness is allowed to trail

## 🔥 Phase 3 — Escalations (20 min — answer ALOUD before opening Phase 4)
- [ ] E1: why is search per-user-shard instead of one global index — and what does that buy at 10GB?
  - Probe: a global index means a global fan-out per keystroke — what does that cost at billions of users?
  - Probe: what query becomes SLOW under per-user-shard search, and why is that trade correct for mail?
- [ ] E2: dedupe and ordering: exactly-once send effects with retries — where are idempotency keys?
  - Probe: SMTP retry duplicates a send — what stops the recipient seeing it twice?
- [ ] E3: spam verdict arrives 2 minutes late — quarantine UX and the unspam learning loop
  - Probe: where does a late-arriving verdict move a message, and what does "not spam" teach?
  - Then raise one escalation YOURSELF — the one you hope they don't ask — and answer it

## 📖 Phase 4 — Reference checkpoints (open only AFTER your attempt)
What a strong L5 answer includes:
- User → shard partitioning; one mailbox lives (mostly) on one shard — the core decision everything else hangs off
  - Say it: "A mailbox lives on one shard with its own index — search fans out within a user, never across the planet."
- Mail = immutable blob + normalized metadata rows — blobs never rewritten, metadata mutated
  - Say it: "The blob is written once; only metadata rows mutate — labels and flags are cheap pointers, not copies."
- Inverted index LOCAL to each user's shard — search fans out only within a mailbox
- Post-indexing is async: search trails arrival by seconds — acceptable, say why
  - Say it: "Indexing is async — search trails arrival by seconds, and for mail that's the right trade."
- Labels are many-to-many → a label index SEPARATE from the message list index
- Threading via Message-ID / References headers, not subject-line guessing
- Push = long-poll/websocket fan-out per user — new mail announces itself
- Sending = durable queue + retries + idempotency keys at delivery targets — retries may re-attempt, never re-deliver
  - Say it: "Retries re-attempt delivery; the idempotency key at the target makes sure they never re-deliver."
- Spam = async ML classifier + feedback loop — "unspam" is a training event, not just a folder move
  - Say it: "The classifier runs async and 'not spam' is a training event — the loop closes with the user."
- Durability: WAL + 3× replication BEFORE ack to sender — "never lose mail" is a write-path property
  - Say it: "WAL plus triple replication BEFORE the sender sees 'sent' — no-lost-mail is a write-path property, not luck."
- Archival tiers for old, cold mail — most mailbox bytes are years old
