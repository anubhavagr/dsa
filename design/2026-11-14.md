- [ ] Non-functional — answer with numbers:

  - 100k-file folders must sync without melting client or server — what breaks first: listing, diffing, or the UI?

  - Every NFR answer ends in a number or a named tradeoff — never an adjective
- [ ] Back-of-envelope done:
  - 1TB at ~250KB average file size → ~4M files per account → metadata rows dwarf blob bytes — say the ratio
  - Sync traffic per change: one 250KB file edited → how many bytes move (hint: not 250KB if you chunk)?
  - Sanity: metadata rows for 1B users × avg files/user → what store survives that?
  - Arithmetic on the page, not in your head — the interviewer grades the working, not the result

## ✏️ Phase 2 — One-page design (25 min)
- [ ] API / interface sketch
  - beginUpload(chunk hashes) / commit(metadata); delta(cursor) → changes; notify → push ping
- [ ] Data model + storage choice justified out loud
  - Content-addressable blob store + metadata DB (tree, ACLs, versions) — TWO systems, say why
- [ ] Box-and-arrow diagram — every box gets a one-line reason
  - Keep it ≤8 boxes; past that, group boxes and name the groups
- [ ] Chunked resumable upload with client-computed hashes per chunk
- [ ] Content-hash dedup at the blob store: hash exists = bytes never move again
- [ ] Change journal per user + monotonic cursor: client says "I'm at cursor N", server replies with everything after N
  - Delta sync, not tree diffing — say why tree-walk dies at 100k files
  - The cursor makes sync O(changes), not O(files) — say that sentence exactly
- [ ] Push (websocket/APNs-style) to tell devices a fetch is needed
- [ ] Conflict policy decided — and when you would merge instead
- [ ] Scaling story: partition key chosen + hot spots named
  - Partition metadata by user; blobs by content hash — different keys, different reasons; hot spot = one user with 10 devices
- [ ] Failure story: what's lost on crash, replication, honest CAP position
  - Blob durable before metadata commit points at it; orphaned blobs are GC'd, dangling metadata is forbidden

## 🔥 Phase 3 — Escalations (20 min — answer ALOUD before opening Phase 4)
- [ ] E1: the same 1GB file is uploaded by 1M users — what makes each upload instant?
  - Probe: what does the server compare, and what must be true about your hashing for "instant" to be safe?
  - Probe: what EXACTLY crosses the network the second time — and what proves it was the same file?
- [ ] E2: two devices edit offline — why 'conflict copy' instead of merging, and when would you merge?
  - Probe: binary vs text — which CAN you merge, and what does the user lose either way?
- [ ] E3: share a folder with 1000 people — what does the read path cache?
  - Probe: ACL check on every file read? Keyed by what, invalidated when?
  - Then raise one escalation YOURSELF — the one you hope they don't ask — and answer it

## 📖 Phase 4 — Reference checkpoints (open only AFTER your attempt)
What a strong L5 answer includes:
- Chunked resumable uploads with client-computed hashes per chunk — resume at chunk granularity
- Content-addressable blob store → dedup: hash exists = instant upload, bytes never re-sent
  - Say it: "Hash exists = instant upload — the bytes are already in the store; only metadata gets written."
- The small-file problem named: 4M × 250KB means metadata dominates — pack small files or accept metadata dominance, but SAY it
  - Say it: "Four million files at 250KB — metadata rows dominate the system; the design leans on the journal, not the tree."
- Client keeps a local DB (SQLite-style) mirroring server state — sync is DB-to-journal, never full-tree scans
  - Say it: "The client mirrors server state in a local DB — sync is journal-to-journal, never a tree walk."
- Delta sync via per-user change journal + monotonic cursor ("I'm at cursor N")
  - Say it: "The client says 'I'm at cursor N'; the server replies with everything after N — nothing else."
- Push via websocket/APNs-style ping that triggers a delta fetch — pull the deltas, don't push file bytes
- Conflicts → explicit conflict copies (simplicity, predictability); text formats COULD merge, binary cannot — when to merge stated
  - Say it: "Two offline edits produce a conflict copy — predictable beats clever for binary files; text COULD merge and I'd say when."
- Sharing = ACL inheritance in metadata; read-path ACL cache keyed by principal, invalidated on share changes
  - Say it: "ACL checks are cached per principal and invalidated on share changes — a 1000-person folder read doesn't do 1000 checks."
- Version history = retained blobs + metadata rows, retention policy + trash semantics
- Mobile = batched deltas, delta compression, wifi-only defaults — bandwidth is a requirement, not an afterthought
