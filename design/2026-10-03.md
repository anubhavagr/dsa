## 📋 Phase 1 — Requirements (15 min, closed-book — write BEFORE looking at Phase 4)
- [ ] Functional requirements (3–5). Starters — complete/extend:
  - Create a short link from a long URL
  - Redirect: code → long URL
  - Custom alias (user-chosen code)
  - Expiry (optional per link)
  - Click analytics
  - Your additions — say which are P0 for 25 minutes of design and which you defer
  - Restate the P0s in one crisp sentence before extending: "create, redirect, alias — analytics and expiry are P1"
  - Name one adjacent feature you deliberately EXCLUDE, with one sentence why (e.g. QR codes, link-in-bio pages)
- [ ] Non-functional — answer with numbers:
  - Read:write ratio you design for — and why 100:1 shapes every layer below it
  - p99 redirect latency target — what does the user actually feel on a bad phone connection?
  - Availability vs consistency: redirects may serve a stale entry, but creations may never fail silently — which CAP position does that buy you?
  - Every NFR answer ends in a number or a named tradeoff — never an adjective
- [ ] Back-of-envelope done:
  - 10⁴ new links/s → how many links/day?
  - Bytes per record (code + long URL + metadata) → storage/day?
  - At 100:1 read:write → QPS on the redirect path?
  - Sanity: does the store fit on one node? For how many years?
  - Arithmetic on the page, not in your head — the interviewer grades the working, not the result

## ✏️ Phase 2 — One-page design (25 min)
- [ ] API / interface sketch
  - createLink(long_url, custom_alias?, expiry?) → code; redirect(code) → 30x; error cases: alias taken, link expired
- [ ] Data model + storage choice justified out loud
  - One record keyed by code; KV (DynamoDB/Bigtable-style) vs relational — the get-by-code access pattern decides it
- [ ] Box-and-arrow diagram — every box gets a one-line reason
  - Keep it ≤8 boxes; past that, group boxes and name the groups
- [ ] ID generation compared out loud, then a winner picked for YOUR write rate:
  - Auto-increment — simple, but a single serialization point
  - Hash-then-collision-check — no coordination, collisions bite at scale
  - Range-allocating ticket server — amortized coordination, each server burns a range
  - Snowflake — local time-ordered 64-bit generation, zero coordination
- [ ] Base62 encoding of the ID space → short-code length (62⁶ vs 62⁷ vs 62⁸ — how much headroom?)
- [ ] 301 vs 302 decided as a tradeoff: cacheability vs analytics
- [ ] Cache layer for hot links — placement, eviction, invalidation
  - Name the eviction policy and the invalidation trigger in the same breath
- [ ] Shard key chosen — and what stays hot
- [ ] Scaling story: partition key chosen + hot spots named
  - Name them: sequential IDs → hottest last partition; one viral code → one shard
- [ ] Failure story: what's lost on crash, replication, honest CAP position
  - Replicate before acking a creation; a missed cache is latency, not correctness

## 🔥 Phase 3 — Escalations (20 min — answer ALOUD before opening Phase 4)
- [ ] E1: 10⁴ creations/s — where's the write contention, and which ID scheme survives it?
  - Probe: name the single-writer bottlenecks before naming fixes
  - Probe: which single component is the serialization point at 10⁴/s — DB, ID generator, or the alias uniqueness check?
- [ ] E2: one celebrity link at 100k reads/s — what absorbs it before the DB?
  - Probe: what happens the moment that entry's cache TTL expires mid-spike?
- [ ] E3: GDPR delete + expiry — lazy delete, TTL sweeps, and what breaks in the cache
  - Probe: a deleted-but-cached link still redirecting for minutes — acceptable or not?
  - Then raise one escalation YOURSELF — the one you hope they don't ask — and answer it

## 📖 Phase 4 — Reference checkpoints (open only AFTER your attempt)
What a strong L5 answer includes:
- Base62 of a counter (or any 64-bit ID) is the encoding floor — 62⁷ ≈ 3.5 trillion codes in 7 characters
  - Say it: "Seven base62 characters is 62⁷ — three and a half trillion codes — decades of headroom at 864M/day."
- Hash-then-collision-check is acceptable at low creation rates; at 10⁴/s the retries and hot partitions bite
- High write rates want ticket-server range allocation or Snowflake-style local IDs — no single sequence in the hot path
- A KV store (DynamoDB/Bigtable-style) fits: short code is the key, record is the value
  - Say it: "The access pattern is get-by-code — I'm not paying for a query planner."
- Redis LRU hot-link cache in front, with event-driven invalidation on update/delete
  - Say it: "The cache exists for the celebrity-link escalation before it's asked — 100k reads/s never reaches the DB."
- 301 caches at browser/CDN — cheap but loses per-click analytics; 302 keeps every hit observable at higher origin load — pick one and defend it
  - Say it: "301 pushes caching to browser and CDN and loses per-click analytics; 302 keeps every hit observable and costs origin load."
- Click analytics = async events into a stream (Kafka-like) → downstream aggregation; NEVER inline work on the redirect path
  - Say it: "Analytics never touches the redirect path — fire the event, move on."
- Custom alias = reserved-word check + a separate uniqueness namespace so aliases can't collide with generated codes
- Envelope said cold: 10⁴/s ≈ 864M links/day × ~100 B ≈ ~86 GB/day of records
  - Say it: "Ten thousand creations a second is 864 million a day, ~86 GB of records — storage is a non-problem; ID generation is the real problem."
- Monitor shortening success rate + redirect p99 — the two numbers the business feels
