## 📋 Phase 1 — Requirements (15 min, closed-book — write BEFORE looking at Phase 4)
- [ ] Functional requirements (3–5). Starters — complete/extend:
  - Limit per user
  - Limit per API key
  - Multiple limit classes (free / pro / API tiers)
  - Headers telling clients their state (remaining, reset, limit)
  - Your additions — admin overrides? burst upgrades? deny-lists? Which do you defer?
  - Restate the P0s in one crisp sentence before extending: "limit per user and per key, tiered classes, honest headers"
  - Name one adjacent feature you deliberately EXCLUDE, with one sentence why (e.g. org-level global budgets)
- [ ] Non-functional — answer with numbers:
  - Limit decision in <5 ms — what does that budget rule out (how many network hops can you afford)?
  - Limit accuracy vs availability: when the limiter's store is down, do you block everyone or let everyone through?
  - Which of your limit classes may fail open, and which must never — and why?
  - Every NFR answer ends in a number or a named tradeoff — never an adjective
- [ ] Back-of-envelope done:
  - 10⁶ requests/s across the fleet → decisions/s the limiter tier must sustain
  - 10⁷ active keys → memory per key budget (what does one token bucket cost in bytes?)
  - Sanity: can EVERY request afford a Redis round-trip? At what QPS does that stop being true?
  - Arithmetic on the page, not in your head — the interviewer grades the working, not the result

## ✏️ Phase 2 — One-page design (25 min)
- [ ] API / interface sketch
  - The limiter as middleware/library + the response contract: 429, Retry-After, X-RateLimit-* headers
- [ ] Data model + storage choice justified out loud
  - Per-key state (tokens + last refill, or window counters) — Redis vs local memory vs hybrid; say the memory number
- [ ] Box-and-arrow diagram — every box gets a one-line reason
  - Keep it ≤8 boxes; past that, group boxes and name the groups
- [ ] Algorithm table built out loud — burst behavior + memory per key:
  - Token bucket — bursts allowed, O(1) state per key
  - Sliding window log — exact, memory-heavy
  - Sliding window counter — the pragmatic hybrid
  - Fixed window — cheap, bursts at boundaries
- [ ] Redis + Lua atomicity vs local counters — decided and defended
  - Lua = atomic check-and-decrement; local = fast but per-instance truth
- [ ] Fail-open vs fail-closed decision — per limit class, with the reason
  - Attach the decision to a NAMED class: "user-facing = fail-open, abuse = fail-closed"
- [ ] Scaling story: partition key chosen + hot spots named
  - Key-hash partitioning; the hot key problem named BEFORE Phase 3 raises it
- [ ] Failure story: what's lost on crash, replication, honest CAP position
  - Redis down: what's the blast radius of fail-open for each class?

## 🔥 Phase 3 — Escalations (20 min — answer ALOUD before opening Phase 4)
- [ ] E1: sticky vs non-sticky load balancing — what does each do to limit accuracy, and what's the middle path?
  - Probe: sticky = accurate limits, uneven fleet; non-sticky = the opposite — what merges the two?
  - Probe: if every instance counts independently at 1/10 of the limit, what's the worst-case overshoot you just accepted?
- [ ] E2: one API key goes viral (hot key) — Redis falls over; now what?
  - Probe: the fix must keep the LIMIT correct, not just keep Redis alive
- [ ] E3: config change at 10k instances — how does it roll out without a thundering herd?
  - Probe: what does the config store see if all 10k reload at once?
  - Then raise one escalation YOURSELF — the one you hope they don't ask — and answer it

## 📖 Phase 4 — Reference checkpoints (open only AFTER your attempt)
What a strong L5 answer includes:
- Token bucket allows bursts + O(1) time and memory per key — usually the right default
  - Say it: "Token bucket: O(1) memory per key, bursts up to bucket size, refill rate is the sustained limit."
- Sliding-window log is exact but stores an entry per request — memory-heavy at 10⁶/s
- Sliding-window counter (weighted merge of two fixed windows) is the pragmatic hybrid
- Fixed window bursts at boundaries — a client can spend 2× the limit across a window edge; name that failure
- Redis Lua script = atomic check-and-decrement — eliminates the read-modify-write race
  - Say it: "The Lua script makes check-and-decrement one atomic step — no read-modify-write race between instances."
- Middle path for non-sticky LB: local token buckets per instance + async refill/state sync — eventually consistent, and you state the tolerance
  - Say it: "Local buckets per instance with async state sync — eventually consistent, and the tolerance is a fraction of one burst."
- Fail-open by default for user-facing APIs; fail-closed for abuse/security limits — and you know which of your classes is which
  - Say it: "Fail-open for user-facing limits, fail-closed for abuse — an outage should not become a self-inflicted DDoS either way."
- Hot key → shard the counter per instance + aggregate the verdict, or replicate reads
  - Say it: "Shard the counter across instances and aggregate — the key survives, Redis survives, the limit stays approximately right."
- Config rollout: staged with jitter — never 10k instances reloading simultaneously
- Return 429 + Retry-After + X-RateLimit-* headers — the contract clients build on
  - Say it: "429 with Retry-After and X-RateLimit headers — clients can only behave if the limiter tells the truth about their state."
- Monitor rejection rates per key class AND the limiter's own added latency
